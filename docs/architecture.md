# Architecture by feature

How each feature of MineColonies Vanilla Tweaks is built: which MineColonies or Structurize windows it replaces,
which of their fields and messages it relies on, and how its preview captures are made. The shared mechanisms
(entry points, how a window gets replaced, screen conventions) are in the developer notes, which are not published:
in short, each screen family listens to `ScreenEvent.Opening`, matches MineColonies' window by its exact class and
opens a vanilla `Screen` instead, falling back to MineColonies' window for the session on any error.

## Resource HUD (`client/data`, `client/hud`)
- **Tracker.** `ResourceHudTracker` runs on the client tick (never per frame). Every 10 ticks it rebuilds an immutable `HudSnapshot`.
  - It reproduces exactly what `WindowResourceList#pullResourcesFromHut` does: it reads `BuildingResourcesModuleView.getResources()`, then works on *copies* of `BuildingBuilderResource`, adding player inventory and in-delivery counts, `getAvailabilityStatus()`, and MineColonies' own `ResourceComparator`.
  - It resyncs by sending `MarkBuildingDirtyMessage`, the same message the scroll sends when opened. It sends it only if the player has `Action.MANAGE_HUTS`, otherwise the server posts a "permission denied" chat message.
- **Rendering.** `HudRenderer` caches the layout per snapshot and only draws each frame. It is shared by `ResourceHudLayer` (the GUI layer) and `HudLayoutScreen` (the drag-and-drop editor). The construction line and bar (config `showConstruction`) show the scroll's "used" value (`BuildingResourcesModuleView.getProgress()`: 100 - remaining needed / the work order's total resources, i.e. materials already placed); MineColonies' stage counter is not used, since `setTotalStages` resets it whenever the builder reloads the blueprint. `HudPreview` (source set `preview`) captures `hut_hud` with sample panels.
- **Pinned builders.** `PinnedBuilders` persists pinned builders (`BuilderRef` = dimension + colony id + hut pos), their scroll name, and their screen position as fractions, in `config/mcvanillatweaks-pinned.json`.

## Bug fixes (`client/fixes`)
- `BlockUiWindowHooks`: on the client tick, runs once per BlockUI window. BlockUI calls `onOpened` on the screen's first tick, so the hook runs after MineColonies has filled the window. It widens the hut `prioValue` field (the French text hid the value) and remembers the citizen of citizen windows (`LastCitizen`) for the inventory's side tabs.
- `CitizenInventoryTabs`: on `ScreenEvent.Init.Post`, adds side tabs to `WindowCitizenInventory`. They reproduce `AbstractWindowCitizen`'s tab targets and visibility rules: the job tab needs a work building that is not the library, the debug tab needs `DebugPlayerManager`.

## Citizen screen (`client/citizen`)
Design notes in `docs/interface-colon.md`. A plain vanilla `Screen` replaces MineColonies' citizen windows (config `vanillaCitizenScreen`, default on).
- **Hook.** `CitizenScreens.onScreenOpening` (`ScreenEvent.Opening`) swaps the `BOScreen` of any `AbstractWindowCitizen` for `CitizenScreen` on the matching `CitizenPage`, and `WindowCitizenInventory` for `CitizenInventoryScreen` (same menu). Tabs open pages *through MineColonies' own windows* (`new XWindowCitizen(c).open()`, `OpenInventoryMessage`), so its open/click advancement triggers still fire; `pendingPage` picks our page when two pages share `MainWindowCitizen`. Any `LinkageError`/`RuntimeException` sets `failed` and MineColonies' windows are used for the rest of the session.
- **Frame.** `CitizenFrame` draws what every page shares at fixed positions: creative-inventory top tabs (the requests tab shows the open request count like a stack size), name + gender, an identity line (job - workplace (level)), and the right column (portrait, armour, hands, hearts/food/happiness, current activity). Its geometry is dictated by `ContainerCitizenInventory`, whose slot positions come from the server: citizen grid at x=8, armour at x=223, player inventory at y=36+18·rows. `CitizenInventoryScreen` draws the menu `MENU_Y` (12) px below the frame top to fit the identity line, so every right-column position is offset by `MENU_Y`, and the frame is `MENU_Y + 118 + 18·rows + BOTTOM_EXTRA` tall. Other pages start at `PAGE_Y`, level with the portrait.
- **Pages** (`PageView` subclasses): `OverviewPage` (its "verdict" row is `CitizenDiagnosis`: why the citizen doesn't work or works slowly, from the data view, its visible status and its important/blocking dialogues, worst first, explained on hover; homeless = `CitizenInfo.building` of the home is null, since MineColonies uses `BlockPos.ZERO`); crafters (`CrafterJobView`) add why they are idle or slow, from MineColonies' rules: they only work on their task queue, fed by requests for an enabled recipe that the warehouse (higher resolver priority) can't fill from stock, so an empty queue gives "no order" / "no recipe" / "recipes disabled" (`crafterIdle`, also the crafter tasks page's empty state), and with orders the first pending child request is the awaited ingredient (blocked when the player or retrying resolver holds it); builders (`BuildingBuilder.View` work building) without an order say why none was taken (`builderIdle`: none waiting, manual mode, level too low by `canBuildIgnoringDistance`, farther than `WorkOrderBuilding.canBuild`'s 100 blocks), with one the requests only the player can fill (blocked), else the resources module's missing items; couriers (`DmanJobView`) show their queue, slowed from 10 deliveries, `SkillsPage` (level bars + job XP shares; a skill with two shares shows their sum, since MineColonies adds/removes them independently), `RequestsPage` (row click = details, fulfill/cancel on hover; actions go through the `RequestTreeWindowModule` of the replaced `RequestWindowCitizen`, found with `getModules()`), `HappinessPage`, `FamilyPage` (parents are stored by name only, so they are looked up by name among the colony's citizens).
- **Shared helpers** live in `client/citizen` and are public for the other screens: `Gui` (vanilla sprites, procedural panels, text colours), `Tooltip` (`setAround` puts a row's tooltip under the row instead of over its buttons), `ScrollArea` (dark inset list + creative scroller, `hover` row highlight), `Vitals` (hearts, food, happiness as the villager XP bar), `Dropdown` / `DropdownButton`, `IconButton` (vanilla button with an item icon), `VanillaIcons` (items for skills and activities, status effect icons for moods, scaled item drawing).
- **Dialogues.** `InteractionScreen` replaces `WindowInteraction` (hooked in `CitizenScreens`, private field `citizen`): it walks `getOrderedInteractions()` like MineColonies (hidden dropped, chit-chat after the first skipped except quest dialogues), answers go to `onClientResponseTriggered` with the replaced window as the `BOWindow` argument (handlers only draw in it from `onWindowOpened`, which is not called: the request item, read from `RequestBasedInteraction`'s private `token`, and a visitor's recruitment cost are drawn here instead), and `removed()` sends `InteractionClose` like `onClosed`. MineColonies' window has `MainWindowCitizen` as parent and opens it on every close (escape, cross, out of interactions), so `onClose` opens it too, and a right click on a citizen with nothing visible to say goes straight to the citizen screen (`hasSomethingToSay`, checked in the hook). `CitizenPreview` saves `citizen_interaction.png` with proxy interactions.
- **Fallback.** `CitizenInventoryTabs` is only visible when this screen is disabled or has failed. Keep it working, but put citizen UI changes here.
- **Dev preview.** Source set `preview` (never packaged). It is registered with `@EventBusSubscriber` and the mod's `sourceSet(sourceSets.preview)`, and is gated by `-Dmcvanillatweaks.preview`: `./gradlew runPreview` opens each page with a proxy-mocked citizen at the title screen and saves `run/screenshots/citizen_*.png`, then sets `CitizenPreview.finished` so `TownHallPreview`, `UniversityPreview`, then `HutPreview`, take over. Use it to check layout; real data still needs the user's screenshots.

## Town hall screen (`client/townhall`)
Same approach as the citizen screen (config `vanillaTownHallScreen`, default on); drawing helpers `Gui`, `Tooltip`, `ScrollArea` and `Vitals` are shared from `client/citizen`.
- **Hook.** `TownHallScreens.onScreenOpening` swaps the `BOScreen` of any `AbstractWindowTownHall` (the view comes from the protected `AbstractBuildingWindow.buildingView`, by reflection) for `TownHallScreen` on the matching `TownHallPage`. The happiness tab shares `WindowCitizenPage` with the citizens tab (`pendingPage`).
- **Actions.** Buttons that open a MineColonies dialog press the button of the replaced window (`TownHallScreen.clickSource(id)` -> `AbstractWindowSkeleton.onButtonClicked`, which also sends the GUI click trigger), so the dialog returns to the town hall as before. Other actions send MineColonies' messages directly, with `TownHallScreen.trigger(buttonId)` for the advancement trigger. Pages (`TownHallTab` subclasses) use vanilla `Button`/`EditBox` widgets added in `init()` (re-run on resize, keep state in fields) and hand-drawn rows in `ScrollArea`s.
- **Clipboard.** `ClipboardScreen` (hooked here too; the colony comes from the protected `colony` of `WindowClipBoard`'s request tree module) has four top tabs (`ClipboardScreen.Page`: DASHBOARD, REQUESTS, BUILDINGS, CITIZENS). The clipboard item is linked to a colony by using it on one of its huts; DASHBOARD is the town hall's dashboard, readable anywhere. REQUESTS is MineColonies' clipboard (the player and retrying resolvers' requests); the town hall dashboard's request rows open it. BUILDINGS (`BuildingsView`, bricks) lists every hut by name with level and distance, CITIZENS (`ColonyCitizensView`, player head) every citizen with job and distance (`LocateBeams.position`), each with a search field in the header; a row click toggles its `LocateBeams` beam. The clipboard item reopens the last page used in the session (`ClipboardScreen.lastPage`). MineColonies only updates colony views for players standing in the colony's chunks (`ColonyPackageManager` close subscribers; members get one copy at login), so the header says whether the data is live or how old it is: `ColonyFreshness` (client tick) remembers when the player was last inside each colony (`isCoordInColony`, the server's test).
- **Colony map.** `ColonyMapScreen` replaces `WindowColonyMap` (hooked in `TownHallScreens.openMap`, private fields `building`, `atTownHall`; the prestige ranking window is a mode of the same screen, never opened). Draws the town hall's map items with `MapRenderer` (z=1, above the inset), huts (block icon sized by level, outline for houses with room, "!" for player-only requests, range on hover), citizens from `LocateBeams.position`, players with their face, and the other colonies (`WindowColonyMap.colonies`) when zoomed far out. Drag/scroll, click = `LocateBeams`. `ColonyMapPreview` captures `hut_colonymap` / `hut_colonymap_ranking`.
- **Colony guide.** `ColonyGuide` (client tick): key G (`key.mcvanillatweaks.colony_guide`) opens `ColonyGuideScreen` for the colony the player stands in (`isCoordInColony`), else the closest known one in the dimension; entering someone else's colony (owner UUID differs) shows an action-bar line with its name, owner, hut count and the key, once the huts have arrived, at most every 10 minutes per colony (config `colonyGuideMessage`, beams section). Visitors get the data because MineColonies sends colony views, huts included, to every player standing in the colony's chunks. `ColonyGuideScreen` (clipboard-like light panel, creative tabs): LIST = `BuildingsView` (also the clipboard's page; sort by distance or name, search, distance and direction arrow `LocateBeams.arrow`), PLAN = `ColonyPlanView`: the ground over the huts' bounds plus 32 blocks (max 768) coloured like a vanilla map from the client's loaded chunks (`MapColor` of the top block, shaded by the north neighbour's height; unloaded chunks dark), a `DynamicTexture` released when the screen closes; huts as their block, players in the colony as faces, drag / scroll zoom, click = `LocateBeams`. Header: owner (`getPermissions().getOwnerName()`), hut count, data age when the player is outside (`ColonyFreshness`). Preview: `hut_guide`, `hut_guide_plan` (no world: no ground, no distances).
- **Quest log.** `QuestLogScreen` replaces `WindowQuestLog` (hooked in `TownHallScreens.openQuestLog`; the colony is only kept in the private `moduleMap` containers' `colonyView`): three top tabs (in progress, available, finished) with counts, templates from `IQuestManager.GLOBAL_SERVER_QUESTS`, row click = `LocateBeams` on the quest's citizen (`getQuestTarget`, or the giver for available quests). `QuestLogPreview` captures `hut_questlog_*`.
- **Icons.** `ColonyIcons` (public, also used by the university): hut block of a building, vanilla items for statistics and colony events.
- **Dashboard.** `DashboardTab` (`TownHallPage.DASHBOARD`, beacon icon) has no MineColonies window: it opens through `WindowMainPage` with `pendingPage`. Its content is `DashboardView`, shared with the clipboard's dashboard tab. Cards (citizens/limit, unemployed, homeless, sick, starving), then lines that lead somewhere: citizens whose `CitizenDiagnosis` is blocked/slowed (click = `MainWindowCitizen`), the clipboard's player requests (click = `ClipboardScreen`), work orders not claimed by a builder, built worker huts with no assigned worker (click = `openGui`). Each section is filled in its own try, so missing data hides only that section.
- **Dialogs.** `ColonyRenameScreen` (`WindowTownHallNameEntry`) and `MercenaryScreen` (`WindowTownHallMercenary`), both from the private `colony` field (`TownHallScreens.openDialog`); "back" reopens the town hall.
- **Permissions.** `PermissionsTab` splits MineColonies' 3-page permissions window into four sections (players, ranks and their actions, free blocks, permission events), sending the same `PermissionsMessage.*` / `ChangeFreeToInteractBlockMessage` messages with the same local updates.
- **Preview.** `TownHallPreview` (source set `preview`) runs after `CitizenPreview` with a proxy-mocked colony and a `BuildingTownHall.View` subclass, saves `run/screenshots/townhall_*.png` (one per permissions section, plus an open drop-down and the alliances with connections), then sets `finished`. With no player at the title screen, permission-gated buttons look disabled there. `TownHallScreen` accepts a null source window for this.

## Hut screen (`client/hut`)
Same approach as the town hall (config `vanillaHutScreen`, default on; the university follows `vanillaUniversityScreen`). One `HutScreen` serves every building except the town hall.
- **Hook.** `HutScreens.onScreenOpening` swaps `WindowHutWorkerModulePlaceholder` / `WindowHutMinPlaceholder` / `WindowHutBuilderModule` / `WindowHutLiving` (exact classes: huts with another custom home page keep MineColonies', the barracks' `WindowBarracksBuilding` is swapped too; the builder's is swapped only once the `minecolonies:minecolonies/check_out_guide` advancement is done, read by reflection, otherwise MineColonies shows its guide, `WindowHutGuide`, which `DialogScreens` swaps), `WindowHireWorker` (private field `building`), `WindowAssignCitizen` (houses' residents, private field `building`, -> WORKERS) and the module windows `SettingsModuleWindow`, `WindowStatsModule`, `UniversityModuleWindow`, `WindowListRecipes`, `MinimumStockModuleWindow`, `WindowHutRequestTaskModule`, `ItemListModuleWindow`, `WindowBuilderResModule`, `WorkOrderModuleWindow`, `WarehouseOptionsModuleWindow`, `ToolModuleWindow`, `EntityListModuleWindow`, `WindowHutMinerModule`, `WindowMineGuardModule`, `RestaurantMenuModuleWindow`, `FarmFieldsModuleWindow`, `PlantationFieldsModuleWindow` (exact classes, module from the protected `AbstractModuleWindow.moduleView`). `SpecialAssignmentModuleWindow` (the warehouse's couriers, the miner's quarriers: just a list of assigned citizens) goes to HOME. `WindowHutAllInventory` (private field `building`) -> the STORAGE page (`HutPage.Kind.STORAGE`, a tab only while open), which is `WarehouseTab` with a null module: no rack options, and the hut block itself counts as a container like MineColonies' window. `WindowHutNameEntry` -> `RenameScreen` (also opened directly by HOME, like `InfoScreen`, MineColonies' `WindowInfo` replacement, which keeps no building field so it is not hooked). `WindowResourceList` (the resource scroll; fields `builder`, `warehouseSnapshot`) -> the builder's resources page, the snapshot handed over through `ResourcesTab.pendingSnapshot`. `WindowBuildBuilding` (build options, also opened by the town hall; private field `building`) becomes `BuildScreen`, a standalone screen (no tabs) that reproduces it: style from the hut or its parent, builder drop-down, materials read from the next level's blueprint with `ClientFutureProcessor` like MineColonies (`BuildScreen.previewResources` feeds the preview), upgrade confirmation drawn in the screen when `getHoverWarningForLevel()` is set, removal on a second click; "back" is `openGui(false)`. Before an upgrade or first build, a "what it brings" tab (`UpgradeInfo`, remembered per session) lists conditions checked like the server (`requestUpgrade`: builder's hut of the target level unless it is the builder's hut, the hut's research effect strength) and gains: blueprint feature counts of the current vs next level (beds, storage, furnaces, crafting tables, brewing stands, size; the current level's blueprint is loaded too), research whose `BuildingResearchRequirement` becomes met (`hasBuilding` reproduced with this hut at the target level), the university's new research tier, the restaurant's menu size and new dishes. `UpgradeInfo.previewCounts` feeds the preview. `HutScreens.openOriginal` shows a MineColonies window without swapping it.
- **Tabs.** `HutPage` = HOME, WORKERS (shown when `WorkersTab.modules` finds jobs, filtered like `WindowHireWorker`; for a `LivingBuildingView` it is the residents page, bed icon), or MODULE (every `isPageVisible()` module, in MineColonies' order; the WORKERS tab replaces the hidden worker modules). Assignment modules with a page (couriers, quarriers) get no tab when WORKERS is shown: HOME lists them, WORKERS hires them. Module tabs without a page here open MineColonies' window (tooltip says so). Icons: vanilla items matched on the module class name (`HutScreen.moduleIcon`), or on the id for item and recipe lists, which share a class. Tabs past the first row go under the panel. Pages are `HutTab` subclasses (public, protected API, so the university's `ResearchTab` can extend it). Tabs open pages through MineColonies' windows (`HutScreens.open`), which are then swapped.
- **Adding a page** for a MineColonies module window: add the window's exact class to `HutScreens.MODULE_WINDOWS`, the module view type to `HutScreen.supports` and `createTab`, an icon in `HutScreen.moduleIcon` if the class name doesn't match one, a `HutTab` subclass reproducing the window's logic (decompile it first), lang keys, and a sample in `HutPreview`.
- **Shared pages.**
  - `HomeTab`: list of the citizens of every `IAssignmentModuleView` (click = citizen screen), hire (-> WORKERS) / recall, build (`BuildScreen`), inventory, storage (STORAGE page, or the warehouse's own page), rename (`RenameScreen`), guide (`InfoScreen`), delivery priority and pickup for worker huts (`WorkerBuildingModuleView`); a summary card for huts without workers.
  - `WorkersTab`: job (drop-down when several), hiring mode (DEFAULT/AUTO/MANUAL like MineColonies' cycle), "show employed", citizen rows sorted like MineColonies with hand-drawn hire / fire / pause / restart buttons.
  - `SettingsTab`: one row per `getSettingsToShow()` key, label from `com.minecolonies.coremod.setting.<id>`; `BoolSetting` button, `StringSetting` drop-down (value set then `TriggerSettingMessage`, which carries the whole setting; `BeekeeperCollectionSetting`'s research check is redone since its flag is only set by `setupHandler`), `IntSetting` field, `RecipeSetting` drop-down of the first crafting module's recipes, guard task positions button; other types (`BlockSetting`, add-ons) open MineColonies' window. Scrolls by row (widgets rebuilt).
  - `StatsTab`: building statistics; "type;name" statistics show the item, found by `ColonyIcons.statItem` from its name (the server stores the hover name as it displayed it: client language or English; the restaurant's `food_served_detail` stores the description id, also looked up).
  - `RecipesTab` (`CraftingModuleView`, also the Domum cutter's): list on the left, selected recipe on the right drawn with the crafting table texture's arrow and result slot (grid filled like MineColonies: in order, 4 inputs as 2x2), up/down (shift = to the end) / toggle / remove (built-in recipes need ctrl) with MineColonies' messages, "teach" = `openCraftingGUI`.
  - `StockTab` (`IMinimumStockModuleView`): stock rows with remove, and an add view replacing Structurize's `WindowSelectRes` (search, stack count max 1000, `ItemGrid` of `ItemStackUtils.allItemsPlusInventory`, inventory items first; escape/enter handled through `HutTab.keyPressed`).
  - `TasksTab` (`RequestTaskModuleView`: crafters, couriers, warehouse): read-only queue like `WindowHutRequestTaskModule` (furthest parent from another requester, priority of deliveries, in progress in green).
  - Helpers of the hut pages: `ItemGrid` (creative-style slot grid with scrollbar; optional counts, 100+ drawn at half size, and extra tooltip lines), `Gui.checkbox` (vanilla checkbox sprite for list rows), `Tooltip.set(stack, extraLines)`.
  - `ItemListTab` (`IItemListModuleView`): search, reset, vanilla checkbox per item; a click adds or removes through the module (the florist's view refuses with a chat message at low level); "enabled" is `isAllowedItem != isInverted`, sorted enabled first only on open/search.
  - `ToolTab` (`ToolModuleView`: guard, forester and beekeeper scepters): scepter card (icon, `com.minecolonies.coremod.gui.tooldesc.<item path>`, "get" = `GiveToolMessage`). On guard huts (`AbstractBuildingGuards.View`) it becomes the "patrol" page: mission from the guard `SettingsModuleView` (`GUARD_TASK`, patrol/follow mode, mine), patrol points from `getPatrolTargets()` (the guard position itself is not synced), a click outlines a point (or all, with the button) with `HighlightManager` and closes the screen. The settings page's "positions" button opens it.
  - `EntityListTab` (`IEntityListModuleView`, only the guards' "hostiles"): every monster of `getAllMonsters()` with its spawn egg (`SpawnEggItem.byId`, spawner otherwise) and a checkbox (`Gui.checkbox`); the list is inverted ("listed" = ignored), so checked = attacked. Reset removes each entry with `removeEntity` (MineColonies' `clearEntities` only clears the client copy). `previewMonsters` feeds the preview.
- **Building pages.** Each `HutTab` subclass's javadoc says which MineColonies window it reproduces and with which messages; only the non-obvious parts are listed here.
  - `HomeTab` has one card slot under a shortened worker list, taken by the first that applies: the builder's current construction (`BuilderSite`, computed like the Resource HUD; `MarkBuildingDirtyMessage` only with `MANAGE_HUTS`), the mine (`MinerLevelsTab.module`, only while the level page is visible), the fields (`FieldsModuleView`). A click opens that page. The warehouse adds a storage card under the actions instead, and houses show `getHoverWarningForLevel()` there.
  - Builder: `ResourcesTab` (pin to the HUD; MineColonies' "+" (`TransferItemsRequestMessage` of the missing amount) only works at the hut: not when opened from the resource scroll (`pendingFromScroll`, set by the scroll's hook) and only within 8 blocks of the hut block, otherwise it is greyed with a "go to the hut" tooltip: the user finds giving from anywhere too easy; Domum blocks get a third line with their cutter materials, `DomumMaterials`, not in the HUD (the user wants them only there): material data is keyed by the block's component ids, in the order of `IDoItem.getInputIds()`), `WorkOrdersTab` (cancel deletes the order, so it takes two clicks; filter and order as MineColonies 1.1.1403's `WorkOrderModuleWindow`: shown and in range, then this builder's or, in manual mode, free ones; the current order (`BuildingResourcesModuleView.getWorkOrderId`) first with a green outline and "in progress", then this builder's, then free, each by priority then id).
  - Warehouse: couriers' waiting deliveries come from `DmanJobView.getDataStore().getQueue()` (request data stores are synced to the client). `WarehouseTab` reads the hut's `getContainers()` as client `AbstractTileEntityRack`s, whose whole inventory is synced (unloaded ones are counted apart); an item click is MineColonies' "locate" (`HighlightManager` key `inventoryHighlight`).
  - Guard tower: see `ToolTab` (patrol page) and `EntityListTab` (hostiles) above.
  - Mine: `MinerLevelsTab` (`levelsInfo`: A = built nodes, B = depth, shown + 1 like MineColonies; tab icon ladder since the pickaxe is the workers tab), `MineGuardsTab` (whole guard huts whose `GUARD_TASK` is `PATROL_MINE`, limit 1, 1, 2, 2, 3 by mine level).
  - Houses and the tavern (`LivingBuildingView`): residents live in `LivingBuildingModuleView`, which is not an `IAssignmentModuleView`, so `HomeTab` and `HutScreen.collectTabs` test the view class. `ResidentsTab` is their WORKERS page (bed icon), reproducing `WindowAssignCitizen`: all 4 `HiringMode`s, buttons off while the colony's `AUTO_HOUSING_MODE` or a non-default, non-MANUAL mode assigns homes.
  - Restaurant: `RestaurantMenuTab` (also the nether miner's food) calls MineColonies' public static `RestaurantMenuModuleWindow.getRecipeFromStack` for ingredients, which needs a client level; ingredients are a named list with the daily range MineColonies only puts in a tooltip.
  - Fields: `FieldsTab` serves both `FieldsModuleView`s (farmer, plantation); assign / free only work in manual mode, like MineColonies.
  - Graveyard: `GraveyardTab` (graves to collect, names read from the client `TileEntityGrave`, click = highlight; citizens buried, with filled / total plots from 1.1.1403's `getFilledGravePlotCount` / `getTotalGravePlotCount`, left out on older versions). MineColonies gives the module the enchanter's title, so `HutScreen.tabTitle` uses our own.
  - Post box: `WindowPostBoxMain` (its own main window, field `postBoxView`) -> HOME, which is `PostBoxTab` for a `PostBox.View` (item grid, amount, partial delivery, `PostBoxRequestMessage`; a summary of the open requests under the form and a button to their own full-page view, with cancel, each row saying who handles it: `getResolverForRequest` display name, or gold when the player / retrying resolver waits for the player; `previewRequests` feeds the preview); `WindowPostBoxMinStock` -> `StockTab`.
  - Barracks: `WindowBarracksBuilding` and the spies dialog `WindowsBarracksSpies` (field `buildingView`) go to HOME, where `BarracksCard` replaces the summary card: towers (huts whose `getParent()` is the barracks) and guards, raid state, last spawn points worded like MineColonies (from level 3), and the spies button (5 gold from player + barracks rack, only during a raid, two clicks, `HireSpiesMessage`). The rally banner's `WindowBannerRallyGuards` (field `banner`) becomes `RallyBannerScreen` (follows `vanillaHutScreen`; `previewTowers` feeds the preview).
  - Field blocks: `WindowField` (field `tileEntityScarecrow`) becomes `FieldScreen` (seed slot + in-screen picker with MineColonies' candidates, `FarmFieldUpdateSeedMessage`; size plan with -/+ per side instead of cycling buttons, 1-20 a side and 20 in all, `FarmFieldPlotResizeMessage`), `WindowPlantationField` (field `tileEntityPlantationField`) becomes `PlantationFieldScreen` (plants from the block's field types' plantation modules, who works each, repair = `WindowBuildDecoration`). Both follow `vanillaHutScreen` and take a colony override for the preview (`hut_field`, `hut_field_seeds`, `hut_plantation_field`).
  - Nether mine: `ExpeditionTab` (`ExpeditionLogModuleView`, visible once researched): status card (name, status, last known hearts/food from the log's stats, click = citizen screen found by name: the log keeps the entity id, not the citizen id), equipment slots, monsters beaten (spawn eggs), loot `ItemGrid` (lost when KILLED). Refreshes like MineColonies (`MarkBuildingDirtyMessage` on open and 1 s after each update), only with `MANAGE_HUTS`. Its food page is `RestaurantMenuTab`.
  - Enchanter: `EnchanterTab` (huts with a worker module, closest first, checkbox = `addWorker` / `removeWorker`), tab icon experience bottle.
  - Recipe teaching ("teach" on the recipes page): `TeachScreens` swaps MineColonies' container screens `WindowCrafting` / `WindowFurnaceCrafting` / `WindowBrewingstandCrafting` (exact classes, building and `CraftingModuleView` found like MineColonies: `getBuildingView(dim, menu.getPos())`, `getModuleView(menu.getModuleId())`) for `CraftingTeachScreen` / `FurnaceTeachScreen` / `BrewingTeachScreen` on the same menu (vanilla slot geometry, drawn `TeachScreen.SIDE` px right inside a bigger frame). `TeachScreen` adds a list of waiting requests this station can make (`WindowSelectRequest`'s list: player and retrying resolvers' requests and their parents; MineColonies only shows it with JEI, and the user's pack has REI), a click shows the client recipe as vanilla-style ghost items (brewing reads `PotionBrewing.potionMixes` by reflection); the "teach" button says why it can't (`canLearn`, recipe already known, nothing placed) and turns green when the module's recipe count grows. `HutScreens` swaps `DOCraftingWindow` for `DomumTeachScreen` (a plain screen: material slots with a picker of `getListOfMatchingItems(doesItemStackContainsMaterialForSlot)`, materials refused by the module's ingredient validator marked; Domum requests fill the materials in one click; same multi-output `RecipeStorage` as MineColonies). `TeachPreview` captures them (`hut_teach_*`), with a client level allocated by `Unsafe` for the crafting menu.
  - World highlights (`ToolTab`, `WarehouseTab`, `FieldsTab`, `GraveyardTab`) use `HighlightManager` boxes for 60 s and close the screen so the box is visible.

## Citizen names (`names`, `client/names`, `mixin`)
MineColonies draws names on the server (`CitizenData.generateName`, static for new citizens and visitors through `initForNewCivilian`, instance for children from their parents' names; no event fires for births or visitors). `CitizenDataMixin` injects at HEAD of both (optional, `defaultRequire: 0`) and asks `CitizenNaming`, which uses the colony owner's lists and returns null (MineColonies draws) when there are none or on any error.
- **Rules** (`NameGenerator`, chosen with the user): first names split male / female; every first name of the gender equally likely; surname from the same list when it has some, else any enabled list, else MineColonies' name file (same for a missing gender); full names taken in the colony (citizens + visitors) avoided, then first names taken. A child keeps a parent's surname (`surnameOf`: after the first word, MineColonies' "X." initial dropped), so first names are one word (spaces become hyphens). Existing citizens and hired visitors keep their names.
- **Where lists live.** Client: `NameLibrary`: built-in lists = every `assets/<ns>/name_lists/*.json` (resource packs can add some; ours named by `mcvanillatweaks.names.list.<file>`; ours: 6 countries (world), medieval / Ancient Rome / Norse (history), elves / dwarves / orcs (fantasy): invented or historical names only, never characters of known franchises: the mod is public), each with a "category" among `assets/<ns>/name_list_categories/*.json` (icon item, order; name `mcvanillatweaks.names.category.<id>`; unknown = "other", custom lists = "mine"), custom lists and the enabled set in `config/mcvanillatweaks-names.json`. A list may have an "icon" (item id; client only, the server ignores it): custom lists pick it in `IconPickerScreen` (every item in a searchable grid, "default icon"), built-in ones from their file; otherwise a book (built in) or book and quill (own). Nothing enabled by default (MineColonies unchanged). `NameSync` sends the enabled lists (`NameListsPayload`, optional channel, cut in 8000-char parts: serverbound payloads max 32 KiB) on login and when `NameListsScreen` closes after a change; the server stores them per player in the world's `NamePools` SavedData, so a colony uses its owner's last lists while the owner is offline. A player without the mod, or a server without it, means MineColonies names.
- **Screens** (vanilla menu style, not our light panels: the mod's settings look like the game's options). `NameListsScreen` (from the settings' top page) is laid out like Select World: title, search field (list names and the names inside, accents ignored), state line, an `ObjectSelectionList` of category headers (click = open/close, all open while searching) and lists (3 lines, checkbox = ticked, the list's icon, double click = open), two button rows (edit/view, new, import; copy, delete through the game's `ConfirmScreen`, example = `SystemToast` of drawn names, done). `NameListEditScreen` is laid out like Create World (`TabNavigationBar`): a list tab (name field, icon button, use checkbox, counts, export; built-in: copy to edit, export) and one tab per column (add field accepting commas, add / remove buttons, sorted names in an `ObjectSelectionList`). The copy takes the original's place among the ticked lists. `NameFiles` imports / exports .json files: the system file dialog (LWJGL `TinyFileDialogs`, shipped with the game) on its own thread, the result applied on the render thread; files dropped on `NameListsScreen` (`onFilesDrop`) are imported too. Export writes {name, icon, male, female, surnames}; import is forgiving for hand-written files (Gson lenient: comments, unquoted keys; French or English keys, folded; a column may be one comma-separated string; "prenoms" fills both genders; one list, an array, or {"lists": [...]}); each list becomes a new enabled custom list, problems (invalid JSON with its line, no names, too big, 100 lists) go in a toast. `NamesPreview` captures `hut_names`, `hut_names_search`, `hut_names_edit_list`, `hut_names_edit`, `hut_names_builtin`, `hut_names_icon` and logs `[names check]` lines (mixin applied, generator, payload split, import of a hand-written file and of a broken one).
- Not checkable in `runPreview`: an actual citizen getting its name needs a colony (user's in-game test).

## Hungry cook fix (`fixes`, `mixin`)
Server side, like the names (needs the mod on the server; single player: nothing more). In MineColonies 1.1.1403 nobody serves the restaurant's cook (`EntityAIWorkCook.checkForImportantJobs` skips `JobCook`): `EntityAIEatTask.goToHut` lets him eat only from his inventory and his restaurant's racks, and only what `FoodUtils.canEat` allows (cooked, not poisonous, nutrition >= house level + 1 from house level 3). When nothing qualifies it returns DONE without `setJustAte`, and `CitizenAI.shouldEat` keeps answering EATING (its `lastState`) while saturation < 60: the cook stops cooking and starves next to his raw food (the user's report, 1.5.10).
- `EntityAIEatTaskMixin` injects at RETURN of `goToHut` (optional, `defaultRequire: 0`); DONE there only comes from the cook branch. `CookMeals.onNothingToEat` picks the best food in his inventory, else in the restaurant's racks (moves enough to fill him): food his house accepts first, then food on the menu, then the most nourishing; never raw, poisonous or MineColonies crops. He eats it at once (sound, `ItemStackUtils.consumeFood` up to full saturation, `addLastEaten` so his food happiness still sees the lower quality), then `setJustAte(true)` sends him back to work in every case: with nothing cooked he cooks, and MineColonies sends him eating again later (the cook only checks 1 time in 200 at saturation <= 2.5).
- Any `LinkageError` / `RuntimeException` disables it for the session ("Cook meal fix unavailable" in the log). `NamesPreview` logs `[cook check] mixin applied to EntityAIEatTask`; the meal itself needs a colony (user's in-game test).

## Locate beams (`client/locate`)
`LocateButton` (recovery compass) sits at the top right of the citizen screens' header (`CitizenFrame.locateX/Y`, both `CitizenScreen` and `CitizenInventoryScreen`) and of `HutScreen`'s header (there it beams the hut's citizens, `LocateBeams.occupants`: workers of every assignment module or a house's residents, all toggled together, disabled when there are none; the university's research slots are drawn left of it), and as a labelled button in the town hall's citizens tab. It toggles a `LocateBeams` target; adding one closes the screen. `LocateBeams` draws a coloured vanilla beacon beam (`BeaconRenderer.renderBeaconBeam`, `RenderLevelStageEvent` AFTER_TRANSLUCENT_BLOCKS, model view set from the event like Structurize's `WorldRenderMacros`) above each target, widened with distance and pulled in to 80 % of the render distance when further (fog), plus a GUI layer with one line per target at the top centre (direction arrow, name, distance). Citizens follow their client entity (`CitizenInfo.entity`), else `ICitizenDataView.getPosition()`; huts use their hut block. Targets go away when reached (3.5 blocks), after 5 minutes, on logout or on a second click. Not checkable in `runPreview` (no world).
`DeathBeams` (config `deathBeams`) gives each grave of the colony views' grave manager (synced to members, what JourneyMap's death points read) a red `LocateBeams.addGrave` beam, once per session: kept while the grave is listed, up to an hour; a grave appearing after the colony's first scan is a death and gets an action-bar message, named from the grave block or the citizen who left the list.

`CompletionMessages` (config `completionClick`: BOTH / BEAM / POSITION / OFF, in the beams section) makes a builder's "finished" chat message clickable. MineColonies sends `entity.builder.message<build|repair|removal>complete` (args: work order name, side of the colony) through `MessageUtils.forCitizen` with a `message.positiondist` hover holding the coordinates (`EntityAIStructureBuilder.sendCompletionMessage`); `ClientChatReceivedEvent.System` finds that part, adds a click event running the client command `/mcvanillatweaks locate x y z` (`RegisterClientCommandsEvent`; chat clicks go through `sendUnsignedCommand`, which NeoForge routes to client commands first) and a hover hint. The command toggles `LocateBeams.toggle(BlockPos, label)` (same key as the hut's own locate button; closes the chat when a beam is added) and/or writes coordinates, distance and direction (8 directions) in the chat. Works on any server. `CompletionPreview` logs `[completion check]` (the message built like MineColonies and sent through the component codec).
